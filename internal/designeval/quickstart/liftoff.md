## 2. 🚀 The 3-Step Liftoff: Your First Agent Run

Surla runs Goa's generator in its sandbox and builds and tests this project in Linux containers, so use its MCP tools on the Surla project server that manages this project rather than running `goa` or `go` commands on your machine:

1. After you edit `design/`, regenerate `gen/` and this guide: the builder calls `generate_code`, and `surla gen -dir <module>` does the same from a shell that is not sandboxed. When a build runs with a test writer (without stored verification settings), the `eval/` test module (`eval/design/` included) belongs to the test writer, and Surla regenerates `eval/gen/` at build start and on each report; after changing `eval/design/`, the test writer reports with `report_tests_finished` to have Surla generate it again, or runs `surla gen -dir eval` from a shell that is not sandboxed. Outside such a build, the builder regenerates `eval/` with `generate_code` and `target: "eval"`.
2. The builder calls `check_project` to build and test the project's uncommitted files. When its message reports a missing `go.sum` or `go.work.sum` entry or a `go.mod` update, the builder calls `update_dependencies` and checks again; `read_check_output` returns the captured output.
3. The builder commits. Every Surla project server has verification configured: `verify_change` runs, against the commit, the tests Surla accepted for the user's build of the change's revision or, with verification settings the user stored with `surla verification set`, their evaluator suite. The builder passes the commit as `candidate_commit` with the `change_id` and `request_revision` of the confirmed Change Card (the guide proposes the card with `propose_change`, and the user confirms it on the views page); without stored verification settings, `verify_change` is refused until the user has built that revision and Surla has accepted the test writer's tests, as the builder's assignment shows. It returns a `run_id`; call `get_verification` with it to read the run's state and result. With the same configuration, `start_live_target` runs a commit as a live target so `draft_override` can try prompt wording on it.

Surla does not run `goa example`. When this project contains the files it scaffolds, such as `cmd/<service>/main.go`, `internal/agents/<service>/bootstrap/bootstrap.go` and `internal/agents/<agent>/planner/planner.go`, they are yours to edit, and the rest of this part explains what they do.
